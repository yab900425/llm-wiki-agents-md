AGENTS.md：寫給 AI 看的專案說明書

用 LLM Wiki 整理 5 份資料，再做成的簡報

先從一個問題開始

AI 每次開新對話，都像新來的同事

  • 你昨天教過它的專案規則，今天它不一定記得。
  • 所以才需要一份「放在專案裡、每次都讓它先讀」的說明書。
  • Claude Code 的做法：每次開新對話，都會先讀 CLAUDE.md。
依據的 wiki 頁面claude-md.md

是什麼

AGENTS.md＝給 AI 的 README

  • 放在專案裡的一份純 Markdown 檔。
  • README 給人看；AGENTS.md 放 AI 需要的細節（建置、測試、慣例）。
  • 沒有必填欄位，標題自己取。
  • 官網自述超過 60k 個開源專案在用。
依據的 wiki 頁面agents-md.md

裡面要寫什麼

好檔案常涵蓋六個面向

指令

  • 怎麼安裝、建置、測試
  • 指令要帶參數

測試

  • 改完要跑什麼
  • 失敗要修到過

專案結構

  • 哪個資料夾放什麼

程式風格

  • 用一小段範例示範

git 流程

  • commit、PR 的規範

邊界

  • 哪些事不能做

六個面向是 GitHub 一位作者分析 2,500+ 份檔案後的主張，文章沒有公開分析方法，請當成做法建議。

寫法

空泛 vs 具體

空泛（AI 很難照做）具體（可以檢查）
好好排版用 2 個空格縮排
你是一個很有幫助的助理你是文件撰寫員，只改 docs/，不碰 src/
要測試改完跑 npm test，失敗要修到過

兩邊都要支援

CLAUDE.md 只寫一行：@AGENTS.md

# CLAUDE.md
@AGENTS.md

## Claude Code 專屬
- （這裡才寫只有 Claude 需要的事）
  • 共同規則只維護一份（AGENTS.md），不會兩邊越改越不一樣。
  • 也可以用 symlink，但 Windows 上可能變成純文字，所以匯入（@）比較穩。
依據的 wiki 頁面claude-md.md

多份檔案怎麼辦

共通原則：越靠近工作位置越優先

agents.md 官網

  • 讀「最近的那份」
  • 使用者在聊天中直接說的，蓋過一切

Codex

  • 從專案根往下串接
  • 越近的排越後面，所以蓋過前面
  • 每層最多採用一個檔案

Claude Code

  • 祖先目錄的檔案全部串接，不是覆蓋
  • 最近的最後讀
  • 子目錄的檔案用到才載入

三家的機制不同，所以不能一概說「覆蓋」。而且沒有任何來源保證 AI 一定遵守。

依據的 wiki 頁面instruction-priority.md

別寫太長

太長，AI 反而讀不好

  • Codex：預設累積到 32 KiB 就停止讀取；範例把上限調到 65536。
  • 越具體（越靠近工作目錄）的檔案排越後面，反而可能被截掉。
  • Claude Code：建議每份少於 200 行。
  • 解法：大專案把規則拆到子目錄，各放一份。
依據的 wiki 頁面size-limits.md

邊界

把「能做、先問、不能做」分開寫

層級例子
Always do（一律做）寫入 src/ 和 tests/、commit 前先跑測試
Ask first（先問）改資料庫結構、加新套件、改 CI/CD
Never do（不要做）commit 機密、改 node_modules 或 vendor、刪掉失敗的測試

文字只是引導。真的不能發生的事，要用 hook 或權限設定擋住。

延伸：同一個概念放大

AGENTS.md 也能管整個知識庫（LLM Wiki）

raw

  • 原始資料
  • 只增不改，是真相來源

wiki

  • AI 整理的 markdown 頁面
  • 互相連結，會持續更新

schema

  • 就是 AGENTS.md 或 CLAUDE.md
  • 規定怎麼整理、怎麼檢查

三個操作：ingest（放進新資料）、query（用 wiki 回答）、lint（找矛盾與孤兒頁）。這份簡報就是照這套做出來的。

自己檢查一次

寫完 AGENTS.md，問自己 5 件事

  • AI 看得出指令要怎麼跑嗎？（有帶參數的指令）
  • 有沒有寫「不能碰什麼」？
  • 有沒有一段真實範例，而不是只有形容詞？
  • 有沒有互相矛盾、或太長的地方？
  • AI 出錯時，我有把原因補回這份檔案嗎？

這是依前面各頁整理的自我檢查，不是任何來源的原文。
